# Portal 多岗位功能性能优化说明

## 问题分析

用户反馈登录和岗位切换时存在重复的API调用问题：

1. **登录时重复调用**：Login页面和UserMenu组件都调用了用户信息和菜单接口
2. **岗位切换时重复调用**：切换岗位时`api-portal/menus/current`接口被调用3次

## 优化方案

### 1. 登录流程优化

**修改前（Login.tsx）**：
```typescript
// 登录成功后立即获取用户信息和菜单
const userInfo = await getCurrentUser();
const menus = await getCurrentUserMenus();
localStorage.setItem('user_info', JSON.stringify(userInfo));
localStorage.setItem('user_menus', JSON.stringify(menus));
```

**修改后（Login.tsx）**：
```typescript
// 登录成功后只保存token，跳转到主页面
// 用户信息和菜单由UserMenu组件统一加载
message.success('登录成功');
history.push('/dashboard');
```

### 2. 岗位切换流程优化

**修改前的调用链**：
```
PositionSelector.handlePositionChange()
  ├── 调用岗位切换API
  ├── 调用菜单获取API                                                          [第1次]
  ├── onPositionChange() -> UserMenu.handlePositionChange() -> loadUserMenus() [第2次]
  ├── onMenuUpdate() -> UserMenu.loadUserMenus()                              [第3次]
  └── 触发全局事件 -> UserMenu监听器 -> loadUserMenus()                       [第4次]
```

**修改后的调用链（最新简化版）**：
```
PositionSelector.handlePositionChange()
  ├── 直接调用 /menus/current?positionId=xxx                                  [仅1次调用]
  ├── onPositionChange() -> UserMenu.handlePositionChange() [仅更新UI状态]
  └── 触发全局事件(携带菜单数据) -> UserMenu监听器 -> 直接使用菜单数据 [无额外调用]
```

### 3. 具体修改内容

#### 3.1 Login组件优化
- **文件**: `src/pages/Login/index.tsx`
- **修改**: 移除登录成功后的`getCurrentUser`和`getCurrentUserMenus`调用
- **移除导入**: 删除不需要的API导入

#### 3.2 UserMenu组件优化
- **文件**: `src/components/UserMenu/index.tsx`
- **修改1**: `handlePositionChange`方法中移除`loadUserMenus()`调用
- **修改2**: 全局事件监听器中移除`loadUserMenus()`调用
- **保留**: 仅在组件初始化时调用`loadUserData()`

#### 3.3 PositionSelector组件优化
- **文件**: `src/components/PositionSelector/index.tsx`
- **修改1**: 移除独立的`getUserPositions`调用，使用父组件传入的岗位列表
- **修改2**: 调整菜单更新调用顺序，确保只调用一次
- **移除导入**: 删除不需要的`getUserPositions`导入

## 优化效果

### 1. 接口调用次数对比

| 场景 | 优化前 | 优化后 | 减少次数 |
|------|--------|--------|----------|
| 用户登录 | 4次 | 2次 | 减少2次 |
| 岗位切换 | 3次 | 1次 | 减少2次 |

### 2. 详细接口分析

**登录场景**：
- `getCurrentUser`: 2次 → 1次
- `getCurrentUserMenus`: 2次 → 1次

**岗位切换场景**：
- `api-portal/menus/current`: 3次 → 1次

### 3. 性能提升

1. **响应速度提升**: 减少不必要的网络请求
2. **服务器压力减轻**: 降低后端API调用频率
3. **用户体验改善**: 减少重复的loading状态

## 数据流设计

### 统一的数据流架构

```
BasicLayout
  └── UserMenu (统一的数据入口)
      ├── 初始化时加载用户信息和菜单
      ├── 传递岗位列表给PositionSelector
      └── 接收菜单更新回调
          └── PositionSelector
              ├── 接收岗位列表（无需独立加载）
              ├── 处理岗位切换
              └── 单次菜单更新回调
```

### 关键原则

1. **单一数据源**: UserMenu组件作为用户信息和菜单的唯一数据源
2. **单向数据流**: 数据从父组件流向子组件，避免重复加载
3. **事件解耦**: 使用回调和事件机制，但避免重复处理

## 验证方法

### 1. 开发者工具验证
打开浏览器开发者工具Network面板：
- 登录时只应看到2次API调用（登录接口 + 用户信息/菜单）
- 岗位切换时只应看到1次菜单API调用

### 2. 控制台日志验证
查看控制台输出：
- 登录后应只有一次"UserMenu: 获取用户信息响应"日志
- 岗位切换后应只有一次"UserMenu: 获取菜单权限响应"日志

### 3. 功能验证
- 登录功能正常，用户信息正确显示
- 岗位切换功能正常，菜单权限正确更新
- 无重复的loading状态或错误提示

## 注意事项

1. **兼容性**: 保持现有的API接口不变，只优化调用逻辑
2. **错误处理**: 保留原有的错误处理机制
3. **缓存策略**: 可考虑添加适当的缓存机制进一步优化性能

## 问题修复记录

### 重复成功提示问题

**原因分析**: PositionSelector和UserMenu组件都调用了`message.success()`
**解决方案**: 移除UserMenu组件中的重复提示，只在PositionSelector中显示
**修复文件**: `src/components/UserMenu/index.tsx`
