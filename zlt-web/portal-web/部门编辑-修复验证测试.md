# 部门编辑功能修复验证测试

## 🎯 测试目标

验证前端和后端联合修复后，部门编辑功能是否正常工作。

## 📋 测试清单

### 1. 前端显示测试 ✅
- [x] 上级部门显示部门名称（不是ID）
- [x] 部门主管显示"员工姓名 (工号)"格式
- [x] 支持员工搜索功能
- [x] 表单数据正确回填

### 2. 操作类型传递测试
#### 编辑操作
**期望**: `operationType: "edit"`
```json
{
  "id": 123,
  "name": "技术研发部",
  "depNo": "RD001",
  "parentId": "1",
  "directorId": "3",
  "gradeid": 1,
  "operationType": "edit"  // 🔑 关键验证点
}
```

#### 新增操作
**期望**: `operationType: "add"`
```json
{
  "name": "新部门",
  "depNo": "NEW001",
  "parentId": "1",
  "operationType": "add"  // 🔑 关键验证点
}
```

### 3. 后端验证逻辑测试

#### 测试场景 1: 编辑部门保持原编号
**操作**: 编辑现有部门，不修改部门编号
**期望结果**: ✅ 保存成功
**验证方法**: 
1. 打开编辑页面，不修改部门编号
2. 点击保存
3. 应该显示"更新成功"

#### 测试场景 2: 编辑部门修改为其他已存在编号
**操作**: 编辑现有部门，修改为其他部门的编号
**期望结果**: ❌ 保存失败，提示"部门编号已存在"
**验证方法**:
1. 编辑技术部，将编号改为"HR001"（人事部的编号）
2. 点击保存
3. 应该显示"部门编辑失败：部门编号已存在"

#### 测试场景 3: 新增部门使用已存在编号
**操作**: 新增部门，使用已存在的编号
**期望结果**: ❌ 保存失败，提示"部门编号已存在"

#### 测试场景 4: 新增部门使用唯一编号
**操作**: 新增部门，使用全新的编号
**期望结果**: ✅ 保存成功

## 🔍 详细测试步骤

### 步骤 1: 验证前端数据传递
1. 打开浏览器开发者工具，切换到Network标签
2. 点击编辑某个部门
3. 修改部门信息后点击保存
4. 在Network中查看发送的请求数据
5. **验证点**: 确认 `operationType` 字段值为 `"edit"`

### 步骤 2: 验证后端日志
1. 查看后端服务日志
2. **验证点**: 应该看到类似日志：
```
[INFO] 接收到部门保存请求 - 操作类型: edit, ID: 1, 部门名称: xxx, 部门编号: xxx
[INFO] 验证部门数据 - 操作类型: edit, ID: 1, 是否编辑: true
[INFO] 编辑部门编号验证通过 - 编号: xxx, 排除ID: 1
[INFO] 部门保存成功 - ID: 1, 名称: xxx
```

### 步骤 3: 验证编辑保持原编号场景
1. 编辑"技术部"（假设编号为RD001）
2. 修改其他信息，保持编号不变
3. 点击保存
4. **验证点**: 应该成功保存，显示"更新成功"

### 步骤 4: 验证编辑修改为重复编号场景
1. 编辑"技术部"
2. 将编号修改为已存在的其他部门编号（如HR001）
3. 点击保存
4. **验证点**: 应该失败，显示相应错误信息

## 🐛 问题诊断

### 如果仍然出现"部门编号已存在"错误

#### 检查前端传递的数据
```javascript
// 在浏览器控制台查看
console.log('提交的数据:', submitData);
// 确认 operationType 是否为 "edit"
// 确认 id 是否正确传递
```

#### 检查后端日志
```
// 查找以下日志关键词
"接收到部门保存请求"
"验证部门数据"
"编辑部门编号验证"
```

#### 常见问题排查
1. **前端operationType传递错误**: 应该是"edit"而不是"add"
2. **后端ID转换问题**: 确保ID正确转换为Long类型
3. **数据库查询问题**: 确认excludeId参数正确传递
