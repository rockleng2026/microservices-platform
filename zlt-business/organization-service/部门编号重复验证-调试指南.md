# 部门编号重复验证 - 调试指南

## 当前状态

根据用户反馈，部门编辑时仍然出现"部门编号已存在"错误。从最新的请求数据看：

```json
{
  "name": "党建一体机部4",
  "depNo": "RD0011", 
  "parentId": "2",
  "gradeid": 4,
  "tel": "18612345674",
  "address": "xxxxxxx4", 
  "description": "党建一体机部测试4",
  "status": 1,
  "id": "1933186684942409728",  // ✅ 现在是字符串格式
  "operationType": "edit"        // ✅ 操作类型正确
}
```

## 问题分析

### 已修复的问题 ✅
1. **前端ID精度问题** - 现在传递字符串格式的ID
2. **操作类型识别** - 正确传递`operationType: "edit"`
3. **后端验证逻辑** - 增强了操作类型判断

### 可能的问题原因 🔍

#### 1. ID类型转换问题
虽然前端传递字符串ID，但后端接收时可能存在转换问题：
- DTO中字段定义为`Long`类型
- Jackson反序列化可能导致精度问题
- 数据库查询时ID比较可能不匹配

#### 2. 数据库中实际数据问题
可能数据库中确实存在其他部门使用相同编号：
- 数据不一致
- 历史数据问题
- 并发操作导致的重复

## 可能的解决方案

### 方案1：ID类型问题修复

如果是ID类型转换导致的比较问题，修改Mapper中的比较逻辑：

```sql
<select id="existsByDepNo" resultType="java.lang.Boolean">
    SELECT COUNT(*) > 0
    FROM department
    WHERE dep_no = #{depNo} 
        AND delflag = 0
    <if test="excludeId != null">
        AND CAST(id AS CHAR) != CAST(#{excludeId} AS CHAR)
    </if>
</select>
```

### 方案3：增强验证逻辑

在业务逻辑中增加更安全的检查：

```java
// 在validateDepartmentData方法中
if (isEdit && saveDTO.getId() != null) {
    // 编辑时，额外检查当前部门是否存在
    Department currentDept = getById(saveDTO.getId());
    if (currentDept == null) {
        throw new RuntimeException("要编辑的部门不存在");
    }
    
    // 如果编号没有变化，直接跳过编号检查
    if (Objects.equals(currentDept.getDepNo(), saveDTO.getDepNo())) {
        log.info("部门编号未变化，跳过重复检查 - 编号: {}", saveDTO.getDepNo());
        return; // 跳过编号检查
    }
}
```
